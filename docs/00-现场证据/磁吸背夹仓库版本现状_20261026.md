## 3. 历史上"合并一版"是怎么做的
1. **main 上没有切版本的痕迹**：无 tag、无 CHANGELOG、无版本号文件。版本号只在文件名（`PRD_V1.0`）和固件/App 发布名（`release/backclip-1.0` rc21、App 1.0.0+19）里。
2. **真正的做法：旁路集成分支 + 一次性批量合并 + 停在那里。** 依据 `嵌入式/总分支合并与重构方案_20261022.md`（只在集成分支上）：先 `git merge-tree` 试合盘点三个仓库，再按表依次合入 15 条分支（10-22 当天 15 个 merge 提交）。原文："冲突只在 README.md、嵌入式/README.md、业务/AI-Coding业务与进度.md 三个索引文件"，处理办法"两边都保留、新日期在前"。方案里有一张**可勾选表**等用户决定（总分支名、电话秘书是否进、拖拽卸载要不要、待定板块、重构范围）。
3. **固件仓流程更成熟**：`release/backclip-1.1` 由 1.0 + 三条功能分支合成；子集成分支 `feat/aios-entry` 并入 A1～A8、C1、C2 共 15 条 `feat/aios-*`；架构文档写明"每个智能体拿到任务卡…禁止触碰的文件…两个智能体不同时写同一文件；每阶段结束合回 feat/aios-entry"。`feat/aios-entry` 也还没合回 1.1。
4. **重复实现与"补回"痕迹**：
   - GitHub 无父快照夹带了"主题系统""竖屏长按卸载菜单"两批文件，与原分支逐字节相同 → 9 个分支看似都改了这批文件，是假象。
   - 主目录 3 个未跟踪文件与未合并分支内容哈希完全一致 → **手工拷贝代替合并**。
   - 产品说明书三份并行；"PRD V2.0" 版本号用了两次；卸载交互做了两套。
   - 固件仓 `feat/call-secretary` 把另一分支的 TTS 代码拷进自己的提交；App 仓 `claude/app-0.7.0` 与主线是同一能力两份实现（试合冲突 9 文件）。
5. **桌面归档 `11_未合并分支资料/`**：44 个分支 + GitHub-main 的**知识库导出**（`build_archive.py` 10-19 生成，用于上传钉钉/飞书/IMA），不是"决定不合并"。其中 13 个已于 10-22 进集成分支；10-19 后又新增 8 个未合并分支不在归档里。

## 对管理工具设计的启示
1. **以"项目"为单位跨多个仓库**：文档仓 + 固件仓 + App 仓挂在一起，只看 iCloud 仓会漏掉真正的合并。
2. **只读扫描避开 iCloud 空壳**：只用读对象库的命令（`for-each-ref`、`rev-list`、`diff A...B`、`merge-base --is-ancestor`、`merge-tree`）；工作区状态加超时 + `GIT_OPTIONAL_LOCKS=0`，超时标"未知/需下载"，不卡住、不误判。
3. **"已合并"至少三档**：进 main / 进集成分支 / 独立未合并，再加"内容等价但历史不同"。只看 `--no-merged main` 会把 13 个已整合分支算成待办。
4. **集成分支是一等对象**：用户的实际流程就是"开集成分支 → 按勾选表批量合并 → 等决定"。工具应生成并保存这张勾选表、记录试合冲突，并**提醒集成分支还没并回 main**。
5. **三个索引文件是已知冲突点**，规则"两边都保留、新日期在前"可自动化。
6. **跟踪工作树生命周期**：目录名≠分支名、孤儿条目、残留 lock、分支已合并但目录还在、无提交的会话目录 → 只给清理建议，由用户确认。
7. **识别"手工拷贝代替合并"**：比对未跟踪文件与分支内容哈希；比对跨分支同名产物或重复版本号。
8. **远端同步状态显式展示**（分叉 7/5、无上游、59 个从未推送），但遵守 AGENTS.md：**只提示，不自动 push**。
9. **随机分支名配人能读懂的标签**：用首条提交说明、改动最多的目录、最后日期自动生成；桌面应用的会话标题是最佳来源。固件仓 A1～A8 任务卡（文件归属、禁改清单、完成定义）可作并行 AI 分工模板。
10. **验收口径做成状态字段**：已合并 / 已构建 / 宿主测试 / 实机通过，合并本身不等于完成。
