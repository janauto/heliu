# 里程碑验收流程

每个里程碑两道闸门，都以「普通用户能否用它解决问题」为口径，不做恶意注入、不做反复压测。

## 闸门一：Fable 验收（主会话亲自做）
1. 对照该里程碑任务卡的「验收」小节逐条执行，记录实际数字/截图/命令输出。
2. 不通过 → 退回 Opus 修复（同一子代理续聊），再验，最多 3 轮。
3. 通过 → 进入闸门二。

## 闸门二：ChatGPT（Codex）二次验收
- 调用：`codex exec -s read-only --ephemeral -C <仓库> --output-schema docs/04-验收记录/verdict.schema.json -o <结果.json> "<验收任务>"`
- 验收任务模板：
  > 你是这个工具的第一位普通用户（个人开发者，用 Claude 桌面应用并行开很多会话）。请只读地阅读 README 与 docs/02-产品定义/产品定义_v0.1.md 的「怎么算做成」，然后实际运行任务卡里列的命令（只读），判断：它是否真的解决了"合并一版漏功能 / 分支落后 / 没有大版本待办"这三个问题中本里程碑承诺的部分？从用户体验角度指出最影响使用的 3 个问题与 3 条建议。不要做压力测试与异常注入。
- 结论字段：`verdict` ∈ 通过 / 有保留 / 不通过；`blocking_issues[]`、`suggestions[]`、`summary`。
- 「不通过」或「有保留」且含 blocking → 修复后再验，**最多 3 轮**；第 3 轮仍未通过 → 把剩余问题记入本里程碑验收记录的「遗留问题」，继续下一个里程碑。
- 每轮结果文件存 `docs/04-验收记录/M<N>-codex-round<k>.json`，汇总写 `docs/04-验收记录/M<N>.md`。

## 记录模板（M<N>.md）
- 验收日期 / 版本提交号
- 闸门一：逐条结果（通过 / 不通过 + 证据）
- 闸门二：轮次、verdict、blocking、采纳了哪些建议
- 遗留问题
- 结论：进入 M<N+1> / 返工
