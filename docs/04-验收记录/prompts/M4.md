你是「合流（heliu）」的普通用户：个人开发者，在 Claude 桌面应用里同时开十几个会话开发同一个项目。请以用户体验视角验收里程碑 M4「按里程碑合并」，不做压力测试、不做异常注入。**绝对不要对真实的磁吸背夹仓库执行 `release run`；只允许 `preview`（只读）与 `rehearse`（在 ~/.cache 下的克隆上演练）。**

M4 承诺：一句"合并 vX"→ 预演（顺序、冲突、顺延）→ 确认 → 顺序合入集成分支 → 冲突交子代理 → 打 tag → 发布说明 → 未完成项显式顺延；永不 push；可回滚。

步骤：
1. 读 README.md、docs/03-架构/M4-任务卡.md、docs/03-架构/M4-实现说明.md。
2. 在临时 fixture（实现说明给出的脚本）上完整走：`heliu release preview <里程碑>` → 看合并单草稿 → `heliu release run <里程碑> --dry-run` → `--yes` 执行 → 检查集成分支包含了哪些、未完成项是否顺延并标 `rolled_from`、tag 是否存在、发布说明是否生成 → `heliu release rollback <里程碑>` 后引用是否回到旧值。
3. 对真实项目：`heliu release preview vNext --project 磁吸背夹`（只读）看顺序与冲突文件是否可理解；如实现说明提供了已完成的演练报告（rehearse 结果），阅读它并核对其中"真仓库零写入"的证据。
4. 判断：不懂 git 的用户能否从预演输出看懂"会合哪些、为什么这几条要等、哪些会顺延"？确认步骤是否足够醒目？"未推送"提醒是否明确？
5. 按 schema 输出：verdict、summary（3 句内）、solved（版本遗漏：M4 核心——顺延是否显式；分支落后：同步基线是否可预演；大版本待办：沿用 M2/M3）、blocking_issues、suggestions（≤5，面向 M5 接入与打包）。
