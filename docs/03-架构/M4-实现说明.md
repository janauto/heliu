## 3. 合并单格式（样例，节选）
```yaml
---
milestone: v1.2
status: 草稿            # 草稿 | 执行中 | 待续 | 已发布 | 已回滚
integration_branch: integ   # 主仓库的（镜像 repos[] 中那一条）
base_sha: 4a9b749f…
repos: [{repo: docs, label: 文档仓, integration_branch: integ, base_sha: 4a9b749f…, main: main, main_sha: be58…}]
items:
  - {feature: F-0004, title: 进度更新 U, decision: 并入, default_decision: 并入, state: 有冲突, repo: docs,
     branch: feat/fu, branch_sha: ac04…, behind: 4, precheck: {conflicts: [README.md], union: [README.md], other: []}}
  - {feature: F-0006, decision: 顺延, default_decision: 顺延, state: 未完成, detail: 会话等你回答：确认要不要做 B, …}
refs_moved: []        # 执行后：{repo, ref, old, new, time, note}
ledger_changes: []    # 执行后：{feature, from, to, note}（回滚依据）
---
| # | 决定 | 功能 | 仓库 · 分支 | 状态 | 试合冲突 | 说明 / 结果 |
| 5 | [x] 并入 | F-0004 进度更新 U | 文档仓 · `feat/fu` | 有冲突 | union：README.md | 落后集成 4 · 已合入 · → 4a68b11 · union 1 个 |
## 执行记录 / ## 发布说明（执行时追加；预演刷新时原样保留）
```
- **顺序**：已进集成（跳过）→ 无冲突 → 有冲突（只有 union 文件的在前，再按冲突文件数）→ 未能试合 → 未完成 → 无法合并。每项另写 `tier`（与看板 ReleaseTier 同名：in_integration / clean / conflict / precheck_failed / unfinished，外加 unmergeable）与建议动作。
- **默认决定**：可合的「并入」；未能试合「待定」；未完成（绑定会话 blocked / 运行中，或卡片状态 想法 / 开发中）与无法合并（分支不存在、仓库没配集成分支等）「顺延」。
- **汇总行**：`新增待合 N · 已在集成 M · 有冲突 C · 未能试合 F · 未检查 U · 顺延 D`（另有等它 / 不并 / 待定时追加）；新增待合 = 决定并入且不是已进集成 / 有冲突 / 无法合并的。
- **刷新保留**：同一项（卡号 + 仓库 + 分支）若 `decision ≠ default_decision` 视为用户改过，刷新后保留。勾选表每次重生成，直接改表格不生效（文件头写明）。

## 4. 合并机制
1. **安全闸**（全部通过才动手，否则整体中止、什么都不写）：每个要写的仓库，集成分支当前 sha == 合并单 `base_sha`；集成分支（`--to-main` 时含主线）**若在某个 worktree 里检出则中止**——移动被检出的引用会让那个目录看起来「有改动」（磁吸背夹实测：文档仓集成分支检出在 `.claude/worktrees/ai-engineering-content-bfff84`，固件仓 `feat/aios-entry` 检出在 `esp_claw-aios`），`--allow-checked-out` 才继续；目标 tag 已存在则中止（不覆盖）。
2. **无冲突**：`merge-tree --write-tree` → `commit-tree <树> -p <集成> -p <预演时的分支提交>` → `update-ref -m … refs/heads/<集成> <新> <旧>`。合入的是预演时记录的 `branch_sha`，之后的新提交不带进来（结果里注明「分支在预演后又有新提交」）。
3. **有冲突**：`~/.cache/heliu/worktrees/<项目>/<里程碑>/<仓库>` 里 `worktree add --detach`（同一次运行复用，后续项 `reset --hard` 对齐）→ `merge --no-commit --no-ff` →
   union 文件：从 index 取三方（`cat-file -p :1/2/3:<文件>`）→ `merge-file -p --marker-size=32` → 每个冲突块集成侧在前、合入侧在后，块内**每个条目都带日期**时按新日期在前稳定排序（否则保持 union 原序；`union_sort_by_date: false` 时直接 `merge-file --union`）→ `git add`；
   其余冲突交解冲突器（最多 2 轮），之后校验：无未合并路径、无冲突标记、**无冲突的已暂存文件 oid 未被改动**（否则判失败）、丢弃未暂存改动与未跟踪文件 → `commit` → `update-ref`。
4. **checks**（project.yaml，可空）：合并结果在临时 worktree 里逐条 `sh -c` 跑（沙箱内，默认 10 分钟超时）；失败该项「失败·待处理」、**不移动引用**；非 `--yes` 时问「输入 yes 跳过它继续，直接回车 = 停止」。
5. **每次 update-ref 先记后动**：先把 `{ref, old, new}` 写进合并单再执行，失败则删掉记录——中断后 rollback 也能凭「当前值 == new / == old」判断。
6. **收尾**（没有「等它」与未执行项时）：每个仓库 `tag -a <里程碑> -m <摘要> <集成顶端>`；`--to-main` 能快进才 `update-ref` 主线，否则列出主线独有提交数请你决定；功能卡：有顺延/失败绑定 → 下一版 + `rolled_from += [本版]`，全部合入 → 状态「已合入」（快进了主线则「已进主线」；验收档位不动，ADR-5），全部「不并」→ 改为未预约；里程碑 → 已发布；合并单末尾写发布说明（已合入 / 顺延 / 冲突处理 / 旧引用可回滚 / 未推送）。结尾打印「未推送：refs/heads/<集成> 与 refs/tags/<里程碑>（按仓库规矩，推送由你决定）」。
7. **「等它」/「待定」**：本次合入其余项、记 refs_moved，但不打 tag、不顺延、不改「已发布」，合并单状态「待续」、里程碑停在「合并中」；「待定」项结果记「跳过·待定」，不并入也不顺延，留在本版，结尾汇总列出；等它好了 / 确认后重新预演（已合入的显示为已进集成）再执行。
8. **rollback**：refs_moved 逆序：分支引用校验当前值 == new 才 `update-ref ref old new`（== old 视为已回退；其他值说明之后有人动过，停止）；tag 校验指向 heliu 打的那个对象才 `tag -d`；然后 ledger_changes 逆序恢复（卡片发布后又被改过的不动、列出原值），里程碑恢复执行前状态。
9. 执行开始时里程碑先改「合并中」，「下一版」自然指向后一个规划中的版本；没有就新建 vNext（若本版就叫 vNext，新建的是 vNext2）。

## 5. 写模式运行器 `runGitWrite(repo, args, {reason, auditLog, cacheRoot, allowRefs, policy})`
- 白名单：merge-tree（仅 --write-tree）· commit-tree · write-tree · update-ref（必须三参数带旧值、引用在 allowRefs 内，禁 -d/--stdin）· tag（仅 `-a <名> -m … <提交>` 与 `-d <名>`，名在 allowRefs 内，禁 -f/签名）· worktree（仅 `add --detach <缓存内路径>` 与 `remove <缓存内路径>`）· merge / merge-file / add（禁 -A/-f）/ commit（禁 --amend/-a）/ checkout / reset / read-tree（**cwd 必须在 ~/.cache/heliu 内**）· clone（必须 --shared/--reference、源为本地路径、目标在缓存内）。push / fetch / pull / branch / gc / prune / clean / rebase / stash / config 等直接拒绝。
- 每次调用**先写一行审计**到 `<台账>/releases/<里程碑>.log`（时间 · 执行/拒绝 · 原因 · 目录 · 完整参数），失败再补一行退出码。
- 注入 `core.hooksPath=/dev/null`、`commit.gpgSign/tag.gpgSign=false`、`rerere.enabled=false`、`GIT_EDITOR=true`、`GIT_LFS_SKIP_SMUDGE=1`、`gc.auto=0`；commit 自动加 `--no-verify`；仓库没配 user.name/email 时用 `heliu <heliu@localhost>`。
- 沙箱：`(deny file-write* <所有被管理仓库根与 common dir>)(allow file-write* <目标 common dir> <~/.cache/heliu>)`——SBPL 后写的规则优先（实测确认），所以 heliu 能写对象库/引用，但写不到用户的工作目录与 `.claude/worktrees/*`。解冲突器与 checks 进程也包在同一沙箱里。真实执行时沙箱不可用只警告（白名单仍在）；**演练时沙箱不可用直接拒绝**（见第 7 节）。

- 二进制：`HELIU_CLAUDE_BIN` → 桌面版内置 `…/claude-code/2.1.308/a93ded4b1b47/claude.app/Contents/MacOS/claude` → PATH 里的 `claude`；测试用 `HELIU_RESOLVER_STUB=<脚本>`（`/bin/sh <脚本>`，同参数、同 stdin）。

## 7. 演练（rehearse）与报告摘要

## 9. 偏离任务卡与已知限制
- **按仓库存 base_sha / 集成分支**（任务卡是单个字段）：磁吸背夹三个仓库集成分支各不相同；顶层两个字段镜像主仓库。tag 打在每个实际涉及的仓库上，refs_moved 每条带 repo。
- 里程碑自身的 `integration_branch` 字段暂不使用，以 project.yaml 各仓库的 `integration` 为准；仓库没配集成分支（App 仓）的项「无法合并」并默认顺延——heliu 不会自建集成分支，也不会直接往主线合。
- 「未完成」把卡片状态「开发中/想法」也算进去（任务卡：开发中/等你回答）；sync 生成的草稿卡多数是「开发中」，所以真实合并单里它们默认顺延，做完的卡请改「待合并」或把决定改成「并入」。
- union_files 是项目级、精确路径匹配（NFC 规范化），对所有仓库生效；不支持通配符。排序只在冲突块内、且每个条目都带日期时进行，不改动冲突块以外的内容。
- 只演练主仓库（固件仓、App 仓「未演练」）；多仓库同时执行的路径只在单测（单仓库）里覆盖到逻辑，未在真实多仓库上跑过。
- 解冲突器的真实 Opus 调用因本机 CLI 未登录未能端到端验证（第 6 节）。**补验步骤**：在普通终端执行 `claude login`（或把 `HELIU_CLAUDE_BIN` 指向已登录的 claude）→ `heliu doctor` 看「无头 claude」一项变为可用 → 重跑 `heliu 演练 下一版 --project 磁吸背夹`（文档仓目前没有普通冲突；要看到真实 Opus 解冲突，需要预约一个有普通冲突的分支，例如固件仓的 F-0044，但固件仓暂不在演练范围）。
- 交互确认用 Bun 的 `prompt()`，只在 TTY 下可用；非 TTY 必须 `--yes`。
- 中断恢复：临时 worktree 残留会在下次执行开始时清理；若目录已被手工删除，仓库里可能留下一条可 prune 的 worktree 登记（heliu 不执行 `worktree prune`，因为它会顺带清掉用户的条目），`heliu hygiene` 会报。
