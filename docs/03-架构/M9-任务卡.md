# M9 任务卡：会话入口 · 跨仓配对 · 三仓名实相符

## 用户原话
「我的大部分文件是在固件仓进行操作的，而文档仓为什么是我项目管理的一个主力？我感觉这三块是不是分类的不是很得当？」（2026-10-28，用户已同意按本卡的推荐方案做。）

## 背景（2026-10-28 只读核实；实现时以实测为准）
- 用户开会话总选文档仓目录，桌面应用在 `磁吸背夹/.claude/worktrees/<名字>` 建 worktree + `claude/<名字>` 分支。文档仓 78 条功能分支全绑了会话；固件仓 31 条、App 仓 9 条分支 0 个会话绑定（worktree 在 `~/.cache/backclip-web/esp_claw-<后缀>`、`~/.cache/backclip-app-*`，是仓库根的**兄弟目录**）。
- 78 条文档分支里 38 条相对集成分支 `git diff --name-only` 为空（**这是代理口径**，含「曾有提交已合入」的可能；精确口径见下）——只是会话入口。
- 61 张卡没有一张同时绑文档仓和固件仓：一项固件工作被拆成两件互不相干的事（会话状态挂文档卡，固件分支的合并/落后挂另一张卡或没卡）。frontmatter 本来支持多条 bindings。
- 桌面会话 JSON 的 `writtenBranches`/`gitAnchors` 不含固件/App 仓（80 个会话 0 命中）——**不能用**。对话记录 `~/.claude/projects/*/<cliSessionId>.jsonl`（约 512 MB，中位数 3 MB，最大 43 MB）里 42/80 个会话出现固件/App worktree 绝对路径，次数悬殊可见主导（aios 638 次；a663 214/74 次；keymodel 跨两仓 86/20 次）。

## 一、空壳分支 =「会话入口」（规则只有一套）
- **判定**：复用 `src/core/owncommits.ts` 的 `isZeroCommit`（尚无独有提交），不另造第二套：A 来源分支（git-worktrees.json / 会话 JSON 的 sourceBranch）→ B reflog（出现过提交类条目 = 曾有提交）→ C 结构兜底（tip == 主线/集成 tip）。三个子问题就此作答：
  1. 不是单纯「相对集成分支还是主线」——来源分支优先的三级判定；兜底时主线、集成 tip 都看。
  2. **曾有提交、已全部合入 ≠ 空壳**（reflog 能区分）：那是「已合入」，照原口径走。
  3. **会话还在运行照常判**：空壳是 git 事实的实时判定、不落盘，一提交自动摘帽；入口分支上的会话状态（等你回答/运行中）照常显示，不因空壳而丢。
- 已知边缘：有提交但净 diff 为空（改了又撤、空提交）**不算空壳**，写进实现说明即可，不扩规则。对账说明：核实的 38 条用的是「diff 为空」代理口径，实现后应满足「空壳数 + 已合入数 ≈ 覆盖这 38 条」，以实测为准。
- **落点**：服务端一处判定（候选 = mergedState 为已合入/已进集成的功能分支，约 40 条，复用 `scan.zero` 式缓存随扫描过期；超时判不了 = null，按「未知」处理不卡死），结果放进 `FeatureView.sessionEntry: boolean | null`，星图/结构/总览/待办**只读这个字段，前端不得自己再算**（M8 同口径的教训）。
- **各计数位点逐个点名**（Codex 按此逐页核对）：
  - 星图：空壳不进类型行；每条泳道在类型行之下加一行「会话入口」，默认收成弱星团（空心小点），文案「会话入口 N（M 已配对）」，展开可见每个入口（会话标题 + 状态色）；泳道头 shown/total 改为「工作 N + 会话入口 M」；`counts.unbound`（流浪星）不含空壳。
  - 结构页：空壳不进「还没建卡」也不进「落后需同步」；页脚一行「另有 N 条会话入口分支（M 已配对）」。
  - 总览：引用「还没建卡」的数字与 actions 同口径（不把空壳算进）。
  - 待办/版本列：以卡为单位，口径**不变**；卡只绑空壳分支时既有「尚无提交」标签照旧。
  - 卫生页：`worktree_no_commits`、`merged_worktree_remains` 保留不改。

## 二、配对建议（建议 ≠ 事实，确认后才写台账）
- **证据源**：对话记录 jsonl，按 cliSessionId 定位文件（对 `~/.claude/projects` 建一次目录索引）。**根目录必须可注入**（env `HELIU_TRANSCRIPTS_DIR` 或参数）：单测用伪造样本，真实数据只读原位。
- **匹配集合**：当次对账的各仓库 worktree 路径 + 仓库根（固件 worktree 是兄弟目录，必须用 `git worktree list` 结果，不能只用仓库路径前缀）。局限写明：**worktree 已删除的会话定位不到分支，不出建议**——这是局限，不是缺陷。
- **提取**：逐行流式，先做路径子串匹配，命中的行才 JSON.parse。分类计数（每〔jsonl 文件 × worktree〕一行）：写入类 = Edit/Write/NotebookEdit 的 file_path 落在该 worktree 下，提交类 = Bash 记录 cwd 在该 worktree 下且命令含 `git commit`；其余命中计 reads；各带 lastSeenAt。**不存一个字的对话内容。**
- **缓存**：项目缓存 sqlite（Application Support，Cache 类已拒绝 iCloud）加表 `transcript_evidence(file, mtime_ms, size, cli_session_id, worktree_path, reads, writes, commits, extracted_at)`；(file, mtime, size) 未变整文件跳过；可删可重建。
- **分档**（阈值集中成常量，真实样本校验后定稿）：
  - 强（默认勾选）：对该 worktree 有写入或提交证据，且该 worktree 当前检出分支有独有提交。
  - 中（列出不默认勾）：无写入证据但主导——出现 ≥10 次且占该会话跨仓命中总数 ≥70%。
  - 弱（折叠「更多弱证据」）：其余命中。
  - 每条建议必须带依据原文（如「esp_claw-aios 638 次 · 有写入」）与强弱档；worktree → 分支按**现在检出的分支**，文案写明（分支可能后来换过）。
- **目标卡**：会话 → 卡（卡 bindings.session == 会话 id，或卡绑了该会话的文档仓分支）。有卡 → 建议把固件/App 分支 bind 到那张卡（一个会话可同时出多仓多条）；无卡 → 第二组「需先建卡」：一键用会话标题建卡并同时绑文档 + 固件分支（预约默认下一版，确认时可改）；固件分支已绑在另一张卡 → 降级为提示「已有卡 F-xxxx，如是同一件事请手动处理」，不自动合卡。
- **性能**：全量提取是显式动作（看板按钮 / CLI），后台任务 + 进度，首扫约 512 MB 预算 ≤60s；增量 ≤2s；**绝不在 scan() 或 hook 里触发**。
- **隐私说明三句**（写进实现说明与界面）：只读已归属本项目会话的对话记录文件；缓存只存路径、计数、工具类别、时间戳，不存对话文本；删除缓存文件即删除全部提取结果。

## 三、确认交互与绑定后的呈现
- **看板**：结构页「现在该决定的」加一类「配对待确认 N」，点开配对面板（总览 actions 也给一行入口）。面板按会话分组：会话标题 + 状态、证据、目标卡、待绑分支，复选框强档默认勾，「绑定所选」一次确认多条；首次进入提示先「分析对话记录」（按钮触发提取，显示进度与上次分析时间）。
- **CLI**：`heliu 配对`（列建议，带编号与依据）；`heliu 配对 --确认 <编号|all>`（写台账）；`--重新分析` 强制全量。**MCP**：`heliu_pair`（默认 dry_run 只列；`ids` + `dry_run: false` 写入），对齐 `heliu_after_merge` 的「先列出、确认后写」模式；SKILL 口径同 ③④节：逐条念给用户，确认后再写。
- **卡片多仓**：详情 bindings 列表给徽标——会话入口绑定标「会话入口」，真实工作分支标仓库名；卡正面 repo 标签显示全部仓库。
- **「等你回答」随卡到固件位置**：现有机制已通——卡的灯色由待办分组决定（blocked → 紫），星图 `branchColor(b, card)` 用 card.light、waiting 取 card.needsAction，绑定后固件星自动变紫带「等你」；验收点：固件星悬停能看到会话标题与该仓 worktree 路径（知道去哪回答）。
- **星图画法（防再乱）**：不加常显跨泳道连线——同卡多星已通过星座线汇到同一版本行星隐式关联；选中任一颗时高亮同卡其余星（含会话入口行的入口点），可画临时虚线；已配对的空壳入口默认并入「会话入口 N（M 已配对）」计数，不单独占位。

## 四、改名与文案（label 是用户数据）
- **不整文件重写 project.yaml**（YAML 序列化会丢手写注释）。做法：看板「开始/设置」与 `heliu doctor` 给建议「文档仓 78 条分支约 38 条只是会话入口，建议改名『总仓（会话入口 + 文档）』」；用户确认后 `heliu project set-label <repo> <新名>` 以「精确匹配该 repo 块 `label: …` 一行」的文本级替换写回，匹配不到就提示手动编辑；看板按钮调同一逻辑。
- 接入向导（start 页）与 README 提示：会话都从一个仓库开时，给它起如实的名字。
- 排查界面/CLI 把第一个仓库暗示为「主力」的文案；「主仓库」仅指台账落点处改为「台账仓」或直接写路径。

## 五、hook / Skill / 全局入口
- 【合流】提示（whereamiContext）加一短句（全仓库通用，≤40 字）：「在其他仓库开了分支/worktree，就用 heliu_feature_bind（cwd 传那个 worktree）绑到同一张卡。」纯文案无新 IO，hook 仍 <300ms；**绝不在 hook 里读对话记录**。
- SKILL.md 新小节「⑥ 跨仓库工作」：去另一个仓库改代码、开了分支就绑回本卡；用户说「这些会话其实在改固件」→ `heliu_pair` 列建议、逐条确认。
- `examples/全局入口.md` 第 2 条后加一条：「一个会话可能横跨多个仓库：在哪个仓库做了真实改动，就把那条分支也绑到同一张卡。」同步安装脚本模板（写入 ~/.claude/CLAUDE.md 的链路已有）；**不替用户改已装机器的全局文件**，提示重跑安装脚本。

## 不做什么
- 不自动绑定、不自动建卡——一切建议经用户确认才写台账（只写 bindings/卡，不碰仓库）。
- 不改被管理仓库：不删空壳分支、不移动/删 worktree、不改分支名；git 事实照常可查。
- 不存对话内容；不在 hook / 普通 scan 里扫对话记录。
- 不做卡片合并（两张卡疑似同一件事只提示）。
- 不改 M1 对账三档与 M2「尚无提交」口径（空壳复用它，不另造）。
- 不依赖 writtenBranches 做跨仓配对（已核实 0 命中）。

## 新接口
- `FeatureView.sessionEntry: boolean | null`（服务端一处判定；null = 未知/超时）。
- `GET /api/pairings`（建议 + 上次分析时间）；`POST /api/pairings/analyze`（触发提取，可查进度）；`POST /api/pairings {items}`（确认写入；item = 绑到已有卡，或 `new:{title,milestone}` 建卡并绑）。
- CLI：`heliu 配对 [--确认 <编号|all>] [--重新分析] [--json]`；`heliu project set-label <repo> <名字>`。MCP：`heliu_pair`。
- 缓存：`cache/<项目>.sqlite` 新表 `transcript_evidence`（可删可重建）。

## 分阶段任务
- **A 后端**：① 空壳判定 + `sessionEntry`（候选过滤、随扫描缓存、超时 null）② jsonl 定位与流式提取器（根目录可注入）③ 证据表与增量 ④ 建议生成与分档（含目标卡映射三种情况）⑤ API / CLI / MCP ⑥ `project set-label` 文本级替换。
- **B 前端**：① 星图会话入口行 + 泳道计数改口径 ② 结构页/总览同口径与页脚计数 ③ 配对面板（分析按钮、进度、分组、多选、确认）④ 卡片多仓徽标 + 选中高亮同卡星 ⑤ 改名建议入口。
- **C hook/Skill/文案**：提示短句、SKILL ⑥ 节、全局入口模板与安装脚本、「主力」暗示文案排查。
- **D 文档**：M9-实现说明（隐私三句、阈值表、局限：worktree 已删无法定位分支；38 条代理口径的对账说明）。

## 验收
1. **测试（bun test）**：空壳口径（尚无提交 ✓ / 曾有提交已合入 ✗ / 改了又撤 ✗ / 超时 null）；提取器（伪 jsonl：写入类、提交类、读类、兄弟目录 worktree 的路径匹配）；增量缓存命中跳过；分档阈值；目标卡映射（有卡 / 无卡建卡 / 已绑他卡降级）。
2. **真实数据自验**：复制 `~/Library/Application Support/heliu` 到临时目录做 HELIU_HOME；对话记录只读原位（注入真实根目录）。核对（给区间，**以实测为准**）：空壳 38±5 条，且「空壳 + 已合入」能解释 diff 为空的那批；可配对会话 42±5 个；三个已核实案例必须出现且分档合理（aios 638 次、a663 214/74 次主导、keymodel 跨两仓两条建议）；首扫 ≤60s、增量 ≤2s；一切写入只落在临时 HELIU_HOME。
3. **浏览器**：文档仓泳道只剩工作星约 40 颗 + 一行会话入口（默认视图本就隐藏已进主线的分支，数字以实测为准）；「分析 → 勾选 → 绑定」走完一轮；绑定后固件星带「等你」且悬停可见会话与 worktree；结构页各计数与星图一致；深色、375px。
4. **Codex** 真实用户视角验收 ≤3 轮（`scripts/codex-accept.sh M9 <轮次> --ref <提交>`，冻结快照），记录 `docs/04-验收记录/M9.md`；超 3 轮记录问题继续推进。
