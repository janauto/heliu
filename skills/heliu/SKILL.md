# 合流（heliu）：主控会话怎么用

合流把 **git 分支 × worktree × 桌面会话** 对上账，并在台账里记「功能卡 → 预约到哪一版」。
git 是事实（领先/落后/冲突/是否合入都实时算），台账只记承诺（标题、预约、绑定、验收档位、顺延）。

通用规则：
- 每个 heliu 工具都可以传 `cwd`。会话开头的【合流】提示里给过 `cwd="…"` 就原样传；主控会话不在 worktree 里时可以不传。
- 「下一版」= 第一个「规划中」的版本；没有时登记新点子会自动建 `vNext`（可改名）。
- 工具返回的中文文本可以直接转述给用户；太长会被截断，提示用户在终端跑 `heliu … --json`。

## ① 查待办：「v1.2 还欠什么」「这个预约到哪」

1. 「v1.2 / 下一版 还欠什么」→ `heliu_milestone_todo`（`milestone` 传「v1.2」「1.2」或不传 = 下一版）。
   - 用户问「能不能合 / 会撞什么」时加 `precheck: true`（在临时区试合，不碰仓库），才会分出「有冲突」。
   - 分组按优先级：等你回答 > 有冲突 > 可合并 > 落后需同步 > 停滞 > 开发中 > 尚未关联开发分支。转述时先说每组几条，再列「等你回答」的原文请求（`需要你：…`）。
   - 计入待办只看台账状态（想法/开发中/待合并）。「开发中 · 尚无提交」= 分支刚切出、还没有提交，不是「已合入」。
   - 「可合并 · 已进集成分支 / 已进主线」下面的「建议：是否标为已合入/已进主线」只转述给用户，用户同意后再 `heliu_feature_set_status`。
2. 「这个预约到 1.2」→ 先确定是哪张卡（当前分支的卡看【合流】提示或 `heliu_whereami`；不确定就问用户卡号），再 `heliu_feature_reserve(id, milestone)`。版本不存在会自动新建；已冻结的版本不接新预约，按返回提示告诉用户。
3. 「我有个新点子：X」→ `heliu_feature_add(title="X")`，标题用用户的原话。
   - 用户正在当前分支上做它：保持默认（自动绑定当前分支）。
   - 只是记个想法、不在当前分支做：传 `bind: false`。
   - 回复用户：卡号、预约到哪一版、是否绑定了分支。
4. 「有哪些版本 / 下一版是哪个」→ `heliu_milestone_list`；「项目现在什么情况」→ `heliu_status`；「哪些会话在等我」→ `heliu_sessions`。

## ② 为某个功能开新会话，并把绑定写回功能卡

用桌面应用自带的 `start_session` 工具（`mcp__ccd_session__start_session`）开新会话，顺序固定：

1. **先登记**：卡还不存在时 `heliu_feature_add(title=…, bind=false)`，记下返回的卡号（如 `F-0012`）。主控会话所在分支不是这个功能的分支，所以这里不要自动绑定。
2. **再开会话**：`start_session`，`initiation: "user_asked"`（用户明确要求时），`use_worktree: true`，`branch_name` 用功能的英文短名；`prompt` 里写清需求，并把下面这句**原样**放在 prompt 开头：
   > 你负责功能卡 F-0012『<标题>』。开始工作前先调用 heliu_feature_bind，id="F-0012"，cwd 传你当前的工作目录（会自动绑定你的分支与会话）。
3. **回写绑定**：`start_session` 返回会话 id 后，若新会话已经确定了分支，调用 `heliu_feature_bind(id="F-0012", repo=…, branch=…, session=<返回的会话 id>)`；分支还不知道时不要猜，第 2 步里新会话会自己绑定。之后用 `heliu_milestone_todo` 或 `heliu_whereami(cwd=<新会话目录>)` 确认卡上已有绑定。

## ③ `heliu_sync` 之后：草稿卡逐条报给用户确认

`heliu_sync` 会把「在 worktree 里开发、没有功能卡、也没进主线」的分支建成草稿卡（标题取会话标题，预约下一版，`source: sync`），同一分支只建一次。

1. 先 `heliu_sync(dry_run: true)` 预览，告诉用户「将建 N 张草稿，预约到 X」，等用户同意再 `heliu_sync()` 写入。
2. 写入后**逐条**报给用户（一次最多 10 条，多了分批）：卡号、标题、所在仓库/分支、状态。每条问两件事：标题要不要改？预约到哪一版？
3. 按用户的回答调用：改名 `heliu_feature_set_status(id, title=…)`；改预约 `heliu_feature_reserve(id, milestone)`；用户说「这个不要了」→ `heliu_feature_set_status(id, status="已放弃")`。用户没表态的保持原样，不要替用户决定。

## ④ 禁止事项

- **永不 `git push`、不删分支、不删 worktree、不 `git fetch`、不 checkout/merge/rebase 被管理的仓库**。heliu 对被管理仓库只读；需要这些操作时只给用户建议，由用户自己执行。
- 不手工编辑台账文件（`milestones.yaml`、`features/*.md`）代替工具；改台账一律走 heliu 工具，变更会记进卡片的「变更记录」。
- 不把「已进主线 / 已进集成分支」说成「已验收」：合并状态和验收档位（未 / 已合并 / 已构建 / 宿主测试 / 实机通过）是两回事，验收档位只在用户明确说测过时才改。
- 不替用户决定预约版本、不批量改名或放弃草稿卡；不确定是哪张卡时先问。
- 不要为了「登记」去改分支名、移动目录或改会话标题。
